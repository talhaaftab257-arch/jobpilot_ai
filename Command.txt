# Autonomous Full-Stack Audit, Bug Fixing & Trucking Dispatch Platform Enhancement

Act as a **Senior Full-Stack Engineer, QA Automation Engineer, UI/UX Engineer, Database Architect, and Trucking Dispatch Operations Owner**. Your task is to thoroughly audit, fix, test, and improve the existing trucking dispatch management application.

Do not just provide recommendations or a report. Inspect the existing codebase, understand the architecture, implement the necessary fixes, and verify the complete application workflow.

## 1. Fix the "Run Sync" Button and Automatic Data Synchronization

The existing **Run Sync** button is not working correctly. Investigate and fix the actual root cause.

Requirements:
- Trace the complete flow from the frontend button to the backend API, synchronization service, database, and frontend refresh.
- Fix incorrect event handlers, API endpoints, authentication, request payloads, async operations, database updates, or state-management issues as applicable.
- When Run Sync is clicked, execute the actual synchronization process and update the relevant database records.
- Automatically refresh the frontend after successful synchronization without requiring a manual page reload.
- Display clear loading, progress, success, partial-success, and error states.
- Prevent duplicate sync operations caused by repeated clicks.
- Handle API timeouts, failed requests, missing data, rate limits, and network interruptions.
- Record the last successful sync time, sync status, records processed, records added, updated records, skipped records, and errors.
- Ensure retries do not create duplicate records.
- Preserve existing records when an external source is temporarily unavailable.
- If background synchronization is supported, verify its scheduling, execution, and status reporting.
- Never display a successful sync message unless the backend confirms success.

**Acceptance criteria:** Clicking Run Sync must trigger a real backend operation, persist the correct data, and refresh all affected frontend components automatically.

## 2. Audit Frontend and Backend Data Consistency

Currently, the backend contains important fields such as MC Number, but the frontend does not display the relevant information correctly.

Audit every important entity and field across:
- Database schema and migrations
- Backend models and validation schemas
- API endpoints and response payloads
- Frontend types and interfaces
- Data-fetching hooks and state management
- Tables, detail pages, cards, filters, and search
- Create, edit, view, and delete workflows

Identify fields that exist in the backend but are missing, incorrectly mapped, hidden, or not rendered in the frontend.

Fix the underlying issues instead of adding hardcoded or dummy values.

For every important field, verify that:
1. It exists in the correct database entity.
2. It is returned by the appropriate API.
3. It is mapped correctly in the frontend.
4. It appears on the correct page.
5. It remains accurate after creating, editing, syncing, or refreshing records.

Use proper typing and validation. Do not silently convert missing values into misleading data.

## 7. Autonomous QA and Complete Functional Testing

Act as a senior QA engineer. Test the application systematically rather than assuming that the code works after implementation.

### Frontend Testing
- Every page loads correctly.
- Every navigation link works.
- Every button performs its intended action.
- Run Sync works and updates the UI.
- Forms validate required fields.
- Create, edit, view, and delete operations work where supported.
- Search, filtering, sorting, and pagination work.
- Loading, empty, error, and success states render correctly.
- Tables and detail pages show the correct backend data.
- No broken components, console errors, or unintended layout regressions.

### Backend Testing
- API endpoints return the correct status codes and response structures.
- Authentication and authorization are enforced.
- Request validation rejects invalid data.
- Database writes persist correctly.
- Relationships and constraints work correctly.
- Sync retries do not create duplicates.
- External API failures are handled gracefully.
- Sensitive information is not exposed to unauthorized users.
- Errors are logged without leaking credentials or secrets.

### Integration and Regression Testing
- Test the complete frontend-to-backend-to-database flow.
- Test records created before and after synchronization.
- Verify that frontend data matches persisted database records.
- Test empty datasets, malformed responses, missing fields, duplicate records, and failed external requests.
- Test multiple rapid clicks on Run Sync.
- Check whether existing functionality has broken because of the changes.

Use the testing tools already available in the project, such as unit tests, integration tests, API tests, browser automation, and end-to-end tests.

Create or update automated tests for critical workflows where practical.

Do not claim that a test passed unless it was actually executed and its result was checked.

## 9. Required Execution Workflow

Follow this sequence:

**Phase 1 — Inspect**
- Inspect the repository structure, frontend, backend, database schema, environment configuration, integrations, and existing tests.
- Identify the root cause of Run Sync failure.
- Trace why MC Number and other important fields are missing from the frontend.
- Create a prioritized list of actual issues.

**Phase 2 — Implement**
- Fix the sync workflow.
- Fix missing and incorrectly mapped fields.
- Improve carrier, load, driver, equipment, and broker detail views where relevant.
- Add only justified schema changes and necessary migrations.
- Improve loading states, errors, validation, and UI consistency.

**Phase 3 — Verify**
- Run linting, type checks, builds, automated tests, and relevant API or database tests.
- Start the application if the environment permits.
- Exercise critical workflows end to end.
- Fix any regressions discovered during testing.
- Rerun failed tests after fixing the underlying issue.

**Phase 4 — Final Audit**
- Review the modified files and database changes.
- Confirm that existing data has been preserved.
- Verify that no fake records or placeholder success messages were introduced.
- Document any external integration that could not be tested because credentials or access were unavailable.

Do not stop after inspecting the code or writing a plan. Continue through implementation and verification for as long as the available environment and permissions allow.

Do not ask for approval for routine, reversible code fixes. Ask only when a destructive operation, external cost, production-impacting action, or missing business decision genuinely requires authorization.
