### C. Supabase-specific requirements

- Use `uuid` primary keys and `gen_random_uuid()` where appropriate.
- Use `timestamptz` for timestamps.
- Use foreign keys, unique constraints, check constraints, and indexes.
- Add `created_at` and `updated_at` where appropriate.
- Create an `updated_at` trigger if the application relies on automatic update timestamps.
- Ensure that the database supports the regional resume mapping and the global daily application limit of 30.
- Enforce uniqueness for canonical job identity and duplicate applications.
- Store flexible source metadata in `jsonb`.
- Store resume storage keys and metadata in PostgreSQL, not the PDF contents.
- Never store plaintext passwords or OAuth tokens in ordinary database columns.
- Make the SQL idempotent where practical, but do not silently overwrite existing application data.
- Do not drop or recreate existing tables without checking the current schema and explaining the impact.

### E. Row-Level Security (RLS)

Review the ownership model before enabling policies.

For every user-owned table:
- Enable RLS where the browser-facing Supabase client can access it.
- Create policies that restrict users to their own records.
- Ensure that one user cannot read or modify another user's resumes, job profiles, contacts, application history, or integrations.
- Use `auth.uid()` for ownership checks when using Supabase Auth.
- Never create a policy that permits all anonymous users to read private data.
- Keep backend-only operations on the server and use appropriately restricted credentials.
- Never expose recruiter contact records or user data publicly unless explicitly intended.

If the application uses only a trusted FastAPI backend for database access, explain the selected access model and how database privileges and user authorization will be enforced. Do not enable RLS blindly without making sure the backend can still perform the required operations.
